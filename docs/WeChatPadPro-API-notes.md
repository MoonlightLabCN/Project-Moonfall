# WeChatPadPro 能力调研笔记

> 调研时间：2026-08-05；**2026-08-06 用无头 Chrome 对照 [wx.knowhub.cloud](https://wx.knowhub.cloud/)（WeChatPadProMAX 文档站）校准路径**。
> 来源：knowhub Apifox 文档站、[WeChatPadPro/WeChatPadPro](https://github.com/WeChatPadPro/WeChatPadPro)、LangBot 接入说明等。
>
> ⚠️ 字段命名可能因版本略有差异；客户端 `WeChatPadApiClient` 以 knowhub 主路径为优先，并保留旧别名回退。

## 1. 项目定位

- 不是官方 API，是基于「微信 iPad 协议」（8059 协议）实现的**个人微信自动化/管理工具**，本质是把一台已登录的“iPad 微信”用 HTTP 接口远程操控。
- 自托管部署（Docker Compose 一键起服务，需要 MySQL 5.7+、Redis），也存在托管版（`adminmax.knowhub.cloud` 后台 + 套餐购买 + Token 管理）。
- 支持多账号并行、账号间隔离。
- 官方反复强调**风控**：新设备/新账号登录后需要稳定挂机、避免短时间大量加好友/建群等敏感操作，会有 1 天/7 天/永久等不同等级的限制。这个约束不影响前端 UI，但影响“账号/设备状态”类页面的设计（后续如果做设置页，需要预留“设备状态/风控提示”的位置）。

## 2. 鉴权与登录

调用任何业务接口前需要拿到三样东西：

| 凭证 | 获取方式 | 用途 |
|---|---|---|
| `adminKey` | 服务启动日志里生成 | 仅用于后台管理/生成 token，不参与业务调用 |
| `token`（授权码） | 管理接口 `/admin/GenAuthKey` / `/admin/GanAuthKey1`（建议 `days=365`） | 后续所有业务接口的鉴权参数 |
| `wxid` | 登录成功后拿到的微信身份标识 | 绝大部分业务接口都要带上，用来指定“这是哪个微信号在操作” |

登录流程（knowhub 快速入门四步，已用 headless Chrome 从侧栏/正文确认）：

0. `POST /Admin/GenAuthKey` —— 生成 TokenKey（业务鉴权码）。
1. `POST /Login/GetQRMac` —— 获取 Mac 登录二维码（另有 GetQR / GetQRx / GetQRPadx / GetQRWinUwp 等设备形态）。
2. 客户端展示二维码，用户用手机微信扫码。
3. 轮询 `POST/GET /Login/CheckMacQR`（另有 `/Login/CheckQR`）—— 未扫码 / 已扫码待确认 / 已确认 / 已过期。
4. `POST /Login/Newinit` —— 初始化 session。
5. 部分新设备/风控场景会要求验证码（`/Login/YPayVerificationcode` 等）。

消息 / 好友（knowhub 侧栏确认）：

- 文本：`POST /Msg/SendTxt`（另有 SendApp / SendCDNImg / SendVoice / ShareLocation…）
- 同步：`POST /Msg/Sync`、`POST /Msg/StartAutoSync`
- 通讯录：`POST /Friend/GetContractList`、`/Friend/GetContractDetail`、`/Friend/GetMFriend`
- Webhook：按授权码配置（手机端不便挂公网回调，App 默认轮询 Sync）

➡️ **对前端的启示**：APP 需要一个独立的“扫码登录页”（本次不在范围内），聊天页本身不处理登录，但消息/联系人数据都要以 `wxid` 为准绑定当前账号。

## 3. 消息能力（决定聊天气泡要支持哪些类型）

官方列出的可发送消息类型（README + 群发相关描述综合）：

- 文本消息
- 图片消息
- 语音消息
- 视频消息
- 文件/文档消息（`/api/v1/message/sendFile` 是确认存在的端点）
- 名片消息（分享联系人）
- “动图”（表情包/GIF，微信协议里和图片是分开的类型）
- 链接分享（图文卡片）
- 小程序卡片分享
- 位置消息
- 拍一拍（对某人发送互动提示，属于系统提示类消息）
- 撤回消息（发送后可撤回，接收端表现为一条“XX撤回了一条消息”的系统提示）
- 消息防撤回（机器人侧功能：拦截“对方撤回”事件，仍把原消息展示出来）
- 红包 / 转账（微信支付相关：发红包、发起转账、自动抢红包）—— 这两类在协议层是特殊消息类型，UI 上会各自渲染成红色/橙色的专属卡片气泡

消息**接收**主要靠 **Webhook 推送**，不是前端主动轮询：

- 后台可配置一个回调 URL（`/v1/webhook/Config` 新增/更新配置，`/v1/webhook/List` 查看已配置的 Webhook，`/v1/webhook/Test` 测试联通），微信这边一有新消息/新事件（`message` / `login` / `logout` / `friend_request` 等）就用 HTTP POST 把事件即时推给这个 URL。
- 请求体带 HMAC-SHA256 签名，防止伪造。支持失败重试。
- 也提供 **RabbitMQ 消息队列**接入方式（适合高吞吐/多进程消费）。
- 第三方接入文档（LangBot）里还提到 `wechatpad_ws`（WebSocket 地址）这一配置项，说明部分部署形态下也存在 WebSocket 长连接推送可选（具体是否所有版本都支持，需要以实际部署为准）。

➡️ **对前端的启示**：真实客户端架构应为「本地 App 起一个小型 HTTP 服务器 / 或用 WebSocket 客户端」接收 WeChatPadPro 主动推送的消息事件，而不是短轮询；聊天页的 ViewModel 应该设计成“订阅式”（收到事件 → 插入一条新消息到集合），本次前端用示例数据模拟的就是这个“消息集合被追加”的模型。

## 4. 联系人 / 群组能力

- 通讯录同步、好友列表拉取、好友详情（昵称、备注、头像、地区、标签、微信号/wxid）
- 加好友、删好友、好友请求的自动/手动通过、好友请求事件通过 Webhook 推送
- 标签管理（给联系人打标签分组）
- 群相关：建群、拉人、踢人、群公告、修改群名称/群头像、获取群二维码、拉取群成员列表（含群内昵称，群里可能和好友昵称不同）
- 朋友圈：发布、点赞、评论

➡️ **对前端的启示**：
- 会话列表里的“最近联系人”本质是聊天 session，不等于通讯录；要分开设计 `ChatSession`（会话）和 `Contact`（联系人）两个模型。
- 群聊气泡要能展示“群内昵称”，且需要区分“是不是我自己发的”“对方在群里的昵称/头像”。

## 5. 本次前端设计据此做的取舍

覆盖到 UI 里的消息气泡类型（对应第 3 节列出的能力）：

文本、图片、语音（带时长）、视频（带时长缩略图）、文件（带图标+大小）、位置（地图缩略图+地址）、名片、链接分享、小程序卡片、红包、转账、系统提示（含“撤回”和“拍一拍”）、引用/回复。

会话列表：置顶、免打扰（静音）、未读角标、群聊人数、最后一条消息按类型显示占位文案（如“[图片]”“[语音]”），这些都是真实微信自带、且 WeChatPadPro 数据能提供的字段，不是凭空加的。

暂不覆盖（前端页面范围之外，留给后续做“设置/账号”页时再处理）：登录二维码页、风控状态提示、Webhook/服务端配置界面、支付密码输入等需要真实资金操作的流程（按安全规则，前端只做视觉气泡，不做真实转账/红包操作）。
